# Mini NPU Simulator

Python 콘솔에서 2차원 패턴과 필터의 MAC(Multiply-Accumulate) 점수를 계산하고, Cross와 X 중 어느 패턴에 가까운지 판정하는 과제 프로젝트입니다.

## 실행 방법

Python 3.8 이상에서 프로젝트 폴더로 이동한 뒤 실행합니다.

```text
python main.py
```

`1`을 선택하면 3×3 사용자 입력 모드, `2`를 선택하면 같은 폴더의 `data.json` 분석 모드, `3`은 패턴 생성기, `4`는 2차원/1차원 MAC 비교입니다. 입력 모드에서 직접 입력을 선택하면 필터 A, 필터 B, 비교 패턴을 각각 3행으로 입력하고, 각 행에는 공백 또는 쉼표로 구분한 숫자 3개를 입력합니다. 잘못된 행은 오류 안내 후 해당 행렬을 처음부터 다시 입력받습니다. 생성 패턴 입력을 선택하면 만들어진 3×3 Cross/X 필터를 사용해 판정을 수행합니다.

## 구현 요약

- `src/matrix.py`가 배열의 비어 있음, 행별 열 개수, 숫자 값을 확인하고 두 배열의 크기를 비교합니다.
- `src/mac.py`는 외부 수치 라이브러리 없이 중첩 `for` 반복문으로 같은 위치의 값을 곱하고 누적합니다.
- `src/judge.py`는 `+`, `cross`, `십자가`를 `Cross`로, `x`, `×`를 `X`로 정규화합니다. 필터 키에도 같은 정규화를 적용합니다.
- 두 점수의 차이가 `1e-9`보다 작으면 `UNDECIDED`로 판정합니다. 입력 모드에서는 이를 “판정 불가”로 표시합니다.
- 기본 epsilon은 `1e-9`이며, 실행 전에 환경 변수 `NPU_EPSILON`으로 조절할 수 있습니다. 예: PowerShell에서 `$env:NPU_EPSILON = "1e-6"`을 설정한 뒤 `python main.py`를 실행합니다. Python 코드에서는 `decide(a, b, epsilon=1e-6)`처럼 호출별 지정도 가능합니다.
- JSON 케이스 키 `size_{N}_{idx}`에서 N을 읽고, `filters.size_N`의 필터와 패턴 크기가 일치하는지 확인합니다. 문제가 있는 케이스는 프로그램을 중단하지 않고 해당 케이스만 FAIL로 기록합니다.
- `src/perf.py`는 각 크기에서 MAC 함수 호출만 최소 10회 측정하고 평균·최소·최대·표준편차(ms), 연산 횟수 N²를 표로 출력합니다.
- 보너스 패턴 생성기는 양의 정수 N을 받아 N×N Cross와 X를 생성합니다. Cross는 가운데 행과 열, X는 두 대각선을 1로 설정합니다.
- 보너스 최적화는 2차원 배열을 행 우선 순서의 길이 N² 리스트로 변환하고, 단일 반복문으로 MAC을 계산합니다. 두 구현은 같은 생성 패턴/필터를 각각 10회 계산해 비교합니다.

## 결과 리포트

다음 수치는 Windows 11 x64, CPython 3.14.7 환경에서 2026-11-19에 `python main.py`의 JSON 모드를 한 번 실행해 얻은 예시입니다. 런타임에서는 `Intel64 Family 6 Model 204` 식별자가 보였지만, 이 환경의 권한으로 정확한 CPU 제품명은 조회하지 못했습니다. 시간은 실행 환경과 부하에 따라 달라질 수 있습니다.

| 크기 | MAC 연산 횟수 N² | 평균(ms) | 최소(ms) | 최대(ms) | 표준편차(ms) |
|---:|---:|---:|---:|---:|---:|
| 3×3 | 9 | 0.004020 | 0.003700 | 0.005200 | 0.000421 |
| 5×5 | 25 | 0.007420 | 0.007000 | 0.008900 | 0.000511 |
| 13×13 | 169 | 0.035360 | 0.034900 | 0.036600 | 0.000590 |
| 25×25 | 625 | 0.114510 | 0.112100 | 0.120400 | 0.002318 |

공식 `data.json`의 테스트는 총 6개이며, 결과는 PASS 3개, FAIL 3개입니다.

- `size_5_1`: Cross 0.9, X 0.8999999999999999로 epsilon 이내의 동점이므로 `UNDECIDED`; expected는 X입니다.
- `size_13_2`: Cross 7.499999999999997, X 7.5로 epsilon 이내의 동점이므로 `UNDECIDED`; expected는 Cross입니다.
- `size_25_1`: Cross 4.9, X 4.899999999999999로 epsilon 이내의 동점이므로 `UNDECIDED`; expected는 X입니다.
- 위 세 FAIL은 배열 크기나 키 형식 오류가 아니라, 데이터가 두 필터에 사실상 같은 점수를 주도록 만든 동점 사례입니다. expected 라벨이 있더라도 동점이면 판정 불가 정책을 적용하므로 PASS가 되지 않습니다.
- 나머지 세 케이스는 예측 라벨이 expected와 일치해 PASS입니다. `+`와 `x`를 표준 라벨로 바꾸기 때문에 표기 차이가 비교 결과를 방해하지 않습니다.
- epsilon은 아주 작은 부동소수점 표현 차이를 동점으로 처리합니다. 이를 적용하지 않으면 0.9와 0.8999999999999999 같은 값이 서로 다른 점수로 잘못 판정될 수 있습니다.
- 현재 기본값 `1e-9`는 과제 권장값입니다. 값이 작을수록 거의 같은 점수도 승패를 가를 수 있고, 값이 클수록 더 많은 점수가 동점 처리됩니다. 실험 목적에 맞춰 `NPU_EPSILON`으로 바꾸되, 결과 비교 시 사용한 값을 함께 기록해야 합니다.
- 제공 데이터로 `NPU_EPSILON=1e-20`을 실행하면 세 동점이 모두 Cross/X로 갈리지만, 세 케이스 모두 expected와 달라 FAIL입니다. 이는 epsilon을 너무 작게 잡으면 저장 오차의 방향이 승패로 바뀔 수 있음을 보여줍니다.
- JSON의 키, 필터 누락, 잘못된 행렬 모양 또는 크기 불일치는 케이스 단위 FAIL로 남겨 데이터/스키마 문제와 정상적인 동점 판정을 구분합니다.
- MAC은 N×N 배열의 모든 칸을 한 번씩 처리하므로 연산 횟수는 N²이고 시간 복잡도는 O(N²)입니다.
- 표의 연산 횟수는 9, 25, 169, 625로 크기 제곱에 따라 늘어납니다. 측정 시간도 대체로 증가하지만, 작은 배열에서는 Python 실행 환경의 잡음 때문에 정확히 같은 비율로 늘어나지 않을 수 있습니다.
- 요약은 동점 `UNDECIDED` 수와 실패 원인별 빈도도 별도로 보여줍니다. 사용자 입력 모드는 임의의 필터 A/B를 받으므로 A/B라고 표시하고, JSON 모드는 의미가 정해진 필터를 사용하므로 Cross/X로 표시합니다.
- 성능 수치는 각 크기별 10회 호출의 평균·최소·최대·표준편차입니다. 측정에 포함되는 것은 `mac(pattern, filter_)` 호출뿐입니다. 제외 항목은 다음과 같습니다.
  - JSON 파일 열기와 파싱
  - 입력 행렬 및 필터 생성
  - 2차원 배열을 1차원으로 변환
  - 표 출력과 기타 콘솔 출력
  - 타이머 시작/종료 호출 자체
- 점수는 입력 숫자와 필터 숫자의 곱을 더한 원점수이며 0~1 범위로 정규화하지 않습니다. 같은 입력을 두 필터와 비교한 점수끼리 상대적으로 읽고, 크기나 값의 범위가 다른 문제 사이의 점수를 직접 비교하지 않습니다.

### 대규모 입력 설계: 1000×1000

1000×1000 한 행렬에는 1,000,000개 숫자가 있습니다. 일반적인 64비트 CPython에서 JSON 숫자를 파이썬 `float`와 리스트로 보관한다고 가정하면, 숫자 객체 약 24바이트와 리스트 참조 약 8바이트를 합쳐 행렬 하나가 대략 32MB, 입력 패턴과 Cross/X 필터 세 개가 약 96MB를 차지할 수 있습니다. 여기에 JSON 원문, 리스트 행 객체, 인터프리터와 임시 객체 메모리가 추가됩니다. 실제 사용량은 Python 버전과 데이터에 따라 달라집니다.

25×25에서 관측한 약 0.115ms를 N²에 비례해 단순히 늘리면, 1000×1000 MAC 한 번은 약 0.18초, 두 필터 비교는 약 0.37초로 추정됩니다. 앞선 실행에서는 25×25가 약 0.325ms로 측정되기도 했으므로, 같은 외삽은 한 MAC 약 0.52초, 두 필터 약 1초가 됩니다. 측정 자체의 변동이 보여주는 것처럼 이것은 작은 배열 측정값을 외삽한 거친 추정치입니다. 캐시·메모리 대역폭·데이터 구성·실행 부하 때문에 실제 시간과 다를 수 있으므로, 제출 환경에서 큰 입력을 다루기 전에는 실제 크기와 같은 데이터로 측정해야 합니다.

큰 입력의 우선 최적화 순서는 다음과 같습니다.

1. 먼저 시간과 메모리를 프로파일링하고, JSON 읽기·배열 변환·MAC 계산 시간을 따로 잽니다.
2. 파이썬 `float` 객체가 많은 중첩 리스트 대신 표준 라이브러리 `array('d')`처럼 연속된 숫자 버퍼를 검토합니다. 1,000,000개의 double 값은 약 8MB입니다. `memoryview`는 연속 버퍼를 복사하지 않고 바라보는 방법입니다. 변환 중 원본과 새 배열이 동시에 있으면 일시 메모리는 증가할 수 있습니다.
3. MAC에 필요한 데이터만 읽고, 불필요한 사본과 반복 변환을 줄입니다. 블록 처리는 입력을 나누어 다룰 수 있을 때 메모리 사용량을 낮출 수 있습니다.
4. 병렬 처리는 데이터 복사와 작업 시작 비용까지 포함해 측정한 뒤 도입합니다. Python 스레드는 CPU 계산에서 GIL의 영향을 받고, 프로세스는 큰 배열 전달·복사 비용이 생길 수 있습니다. CPU SIMD 명령을 쓰려면 해당 명령을 사용하는 저수준 구현이나 장치 라이브러리가 필요하며, 현재 순수 Python 반복문이 자동으로 SIMD가 되지는 않습니다.

### CPU와 NPU의 병목

현재 구현은 Python CPU에서 한 번에 한 칸씩 계산합니다. 작은 과제 크기에서는 파이썬 반복문과 인덱스 접근 비용이 산술 자체보다 크게 느껴질 수 있습니다. 큰 행렬에서는 연속되지 않은 메모리 접근과 메모리 대역폭도 병목이 될 수 있습니다. 한편 실제 NPU는 많은 MAC 연산 유닛을 병렬로 사용해 큰 행렬 연산을 동시에 처리하도록 설계됩니다.

NPU를 써도 계산이 항상 빨라지는 것은 아닙니다. 입력 데이터를 NPU 메모리로 옮기는 시간, 데이터 형식 변환, 작업 시작 비용, 메모리 대역폭이 병목이 될 수 있습니다. 작은 3×3 문제에서는 전송·시작 비용이 병렬 계산의 이득보다 클 수 있습니다. `perf_counter`로 CPU 기준을 반복 측정하고, `cProfile`로 Python 함수 시간을 살펴본 뒤 장치 전송 시간과 NPU 커널 계산 시간을 분리해 비교하는 것이 우선입니다. 이 프로젝트에는 NPU 장치 연결이 없으므로 NPU 시간은 측정하지 않고 설계상 차이만 설명합니다.

### 보너스 1: 2차원 / 1차원 MAC 비교

메뉴에서 `4`를 선택하면 같은 생성 데이터와 10회 반복으로 두 구현의 평균 시간을 비교합니다. 2차원 배열을 1차원으로 바꾸는 준비 시간은 측정에서 제외하고, MAC 함수 호출만 잽니다.

| 크기 | 연산 횟수 | 2차원 평균(ms) | 1차원 평균(ms) | 관측 속도비 |
|---:|---:|---:|---:|---:|
| 3×3 | 9 | 0.007170 | 0.000990 | 7.242× |
| 5×5 | 25 | 0.010910 | 0.001420 | 7.683× |
| 13×13 | 169 | 0.050070 | 0.006510 | 7.691× |
| 25×25 | 625 | 0.171020 | 0.026860 | 6.367× |

이번 실행에서는 1차원 구현이 더 짧게 측정됐지만, 작은 데이터에서는 타이머와 Python 실행 환경의 영향이 큽니다. 이 수치는 특정 환경의 한 번 실행한 결과이며 모든 환경에서 같은 비율을 보장하지 않습니다. 두 구현 모두 N²개 값을 곱하고 더하므로 시간 복잡도는 O(N²)입니다. 차이는 배열 접근과 반복문 구조에 있습니다. 이 비교에서는 1차원 변환 비용을 제외하므로, 한 번만 계산할 때는 변환 비용까지 포함해 별도로 판단해야 합니다.

### 보너스 2: 패턴 생성기

메뉴에서 `3`을 선택하고 N을 입력하면 Cross와 X 패턴을 출력합니다. 예를 들어 N=5일 때 Cross는 가운데 행/열, X는 양쪽 대각선에 1이 놓입니다. 메뉴 `1`에서도 생성된 3×3 필터와 패턴을 골라 바로 판정할 수 있고, 일반 성능 측정과 최적화 비교에서도 생성 패턴을 사용합니다.

## 검증 기록

- JSON 모드에서 제공 데이터 6건을 처리해 3 PASS / 3 FAIL 요약과 실패 사유를 확인했습니다.
- 사용자 입력 모드에서 3×3 배열 입력, 두 MAC 점수, 판정, 3×3 성능 표 출력을 확인했습니다.
- 생성기에서 N=5 패턴 출력, 생성된 3×3 패턴으로 사용자 모드 판정, 네 크기의 2차원/1차원 비교 표 출력을 확인했습니다.
- JSON 요약에서 UNDECIDED 수, 실패 사유별 집계, 평균·최소·최대·표준편차 출력도 기록합니다.
- NumPy, pandas 등 외부 라이브러리는 사용하지 않습니다.

### 라벨을 새로 추가하는 방법

새 라벨을 지원하려면 `src/judge.py`의 `normalize_label()`에 해당 문자열을 표준 라벨로 바꾸는 규칙을 추가합니다. 그런 다음 `data.json`에 그 라벨을 쓰는 케이스를 추가하고, JSON 모드에서 예측과 expected가 표준 라벨로 일치하는지 확인합니다. 마지막으로 README의 지원 라벨 목록과 결과 리포트를 갱신합니다. 알 수 없는 라벨은 임의로 추측하지 않고 데이터/스키마 오류로 기록합니다.
